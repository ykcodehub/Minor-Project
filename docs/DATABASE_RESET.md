# Fresh databases and guarded document cleanup

**Preferred production setup:** provision a fresh PostgreSQL database, configure its URL privately, and run `python -m app.manage migrate`. Keep existing development data. This project never resets production automatically.

## Read-only inspection

From backend with the project environment active:

```powershell
python -m app.manage check
python -m alembic check
python -m app.reset_documents
```

The last command is a **read-only plan**. It reports document-table counts, environment, Alembic revision and a non-secret target fingerprint. It performs no deletion or storage cleanup. Do not use a database URL as a command argument or paste it into logs.

## Scope of the optional reset

Only document-derived records: sources, sections, chunks, jobs/discovery payloads, analyses/source links, findings/evidence, model-call metadata, questions, reports and cached translations. Schema/indexes/constraints/migrations remain intact.

**Preserved:** users/passwords/Google identities, sessions, pending registrations, auth/OAuth tokens, user settings, rate buckets, audit records, encryption keys and Alembic history. Existing deletion-outbox entries stay intact. Encrypted objects associated with the selected document records are queued in the durable outbox; the script does not sweep unknown files or empty an S3 bucket. Cleanup retries happen only when a worker is deliberately resumed. Versioned object/backup retention is separate.

## Separate approval and backup gates

This procedure is intentionally unavailable when ENVIRONMENT=production. For an explicitly approved development/staging cleanup only:

1. Obtain **separate user/operator approval** for the exact environment, target and documents-only scope. A request to build/test the app is not approval to reset data.
2. Stop API and workers. Finish or cancel active jobs using normal application controls. The reset refuses queued/processing jobs.
3. Create and verify a real PostgreSQL backup plus the storage/key backup required by your recovery policy. Test restore separately. Never put a backup or approval file in Git.
4. Run the read-only plan and record its fingerprint.
5. The approving user/operator creates a private JSON file with: `approved:true`, `backup_confirmed:true`, `approved_by`, `scope:"documents-only"`, `environment:"development"` or `"staging"`, `database_fingerprint`, and UTC `expires_at` within24 hours. No approval file is generated by this assistant/script.
6. Only after that approval, an operator may run the guarded command with all four explicit inputs:

```text
python -m app.reset_documents --execute --environment <development-or-staging> --backup-file <verified-backup-path> --approval-file <separately-created-approval-path> --confirm "DELETE DOCUMENTS <fingerprint>"
```

The script validates these gates, locks document tables, queues known objects, deletes document records transactionally and commits. It never invokes DROP/TRUNCATE/downgrade or touches account settings/credentials. Keep services stopped until the result is reviewed. Resume the worker only when physical cleanup is approved. Read-only planning was executed during preparation; destructive execution was **not performed**.
